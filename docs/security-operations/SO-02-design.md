## Management workflow
Preserve accepted Employees, Roles, Permission registry and Access explanations screens. Employee selection retains compact name, explicitly synthetic opaque ID, location/status and accessible named details control. Registry retains 20-record page and ten fictional operations. In employee details, show separate sections for current role memberships, direct grants and overriding restrictions. Historical/expired assignments separate from active; pending changes separate from both. Never infer effective access from role names, union rows or calculate restriction outcomes. Show only admitted backend projections. Existing explanation workflow remains independent of execution and approval.
Role configuration: browse/search roles by human label; select exact role, inspect current admitted operation/scope list and revision, propose edits in a separate draft view. Employee membership: choose multiple admitted roles, show explicit additions/removals rather than replace hidden memberships. If complete current set cannot be established, block replace-all semantics. Role edits may affect multiple employees; show backend-admitted affected count and impact, not calculated membership expansion. No hard deletion or role creation unless approved contract explicitly supports it.
Direct grant/restriction editor: select named tool/domain and operation; use approved search/paging, labels primary and canonical identifiers secondary (copyable only when admitted). Distinguish grant versus overriding restriction in text and icon, not color alone. Preserve distinct operation meanings (master cost versus PO line cost, local receipt inspection versus remote reconciliation); unresolved aliases/provisional operations not enabled merely because listed. Only approved selector options. Scope picker uses explicit location/resource/field dimensions and relationships as supplied by Security; no guessed defaults, wildcard, Cartesian expansion, implicit all locations or free-text canonical IDs. Show scope completeness, unsupported dimensions, prerequisites, conflicts, expiry and historical status. Server decides eligibility and effective scope; client validates input shape only. Expiry display uses explicit timezone and unambiguous instant; no invented permanent option or expiry bounds.
## Presentation wireframes (non-executable)
Desktop: left existing navigation; main employee or role header and current context; two-column current access / proposed changes where space permits. Employee card: name, synthetic ID, status/location; role memberships list with named controls; direct grants and restrictions each distinct labeled section; collapsed history; action to review changes only when capability supplied. Operation picker: search by label/tool/domain/operation, grouping and admitted scopes; secondary ID; select and inspect before adding. Mobile: stacked current then proposed, wrapping identifiers, full-width labels, no horizontal scrolling, 44px targets, sticky action only if it cannot obscure focus/content. Preview: target and reason, old/new current-versus-proposed summary, backend gained/lost scopes, affected employees, conflicts, prerequisites, assurance/approval, expiry and confirmation eligibility. Explicit confirm control after review; status panel and independent readback separate. No credential inputs or real employee number. No settings, session/device, audit dashboard or approvals queue (SO-03 or separately gated).
## UI state model (presentation names, not wire enums)
Read current -> edit local intent -> request preview -> review admitted preview -> explicit confirm -> inspect outcome -> independent readback. Editing target/scope/role/reason/expiry or changing revision/policy/context invalidates preview and disables confirm. Context loss hides sensitive data, clears local intent, invalidates generation, no unsafe persisted drafts. A pending request locks duplicate confirmation immediately; retain original immutable request identity only as authorized by approved contract. Confirm is not success: pending approval, required step-up, expired/stale/denied/malformed, unavailable and uncertain outcome each get explicit safe messages. No auto-retry or automatic confirm after reauth; a fresh preview and explicit confirmation only when approved semantics allow. Unknown outcome freezes resubmission and offers independently admitted status inspection; if status reference missing or read denied, stop and show safe recovery instruction without revealing target/result. Committed status alone is not readback; display confirmed synthetic change only after independently authorized matching readback. If commit is known but readback denied, do not imply rollback/failure or repeat change; hide sensitive detail and distinguish reported commit from unavailable verification using only authorized projection. Navigation during outstanding confirm must not silently cancel or resend; discard stale visual responses; later status inspection only per contract. No persistent client cache, no credentials, no permission engine.
## Accessibility and acceptance design
Native controls, field labels and described errors, logical tab order, visible focus, keyboard operation, no color-only statuses, polite live status and explicit error summary; focus first invalid field or preview heading, restore meaningful focus on back; avoid focus theft from superseded responses. Responsive widths desktop 1280 and mobile 390/320; no overflow, long identifiers wrap. Use fictional records only and textContent, preserve CSP connect-src none/form-action none. Existing 43 SO-01 tests remain unchanged and rerun after authorized implementation. Planned regressions: missing/mismatched binding/capability/policy/subject, complete typed scope, preview expiry and revision conflict, input/navigation invalidation, duplicate confirm, delayed success/failure and unknown outcomes, denied status/readback, no auto-resubmit, no optimistic success, safe projection/clear context, no network/credential controls. Tests must use exact approved scripted positive/negative examples, not invented wire responses. Native local checks first; capped CI only if required. Owner browser checklist after release: role/multi-role edits, grant/restriction scope, current/proposed, expiry, preview and explicit confirmation, approval/step-up, status/readback denial, duplicate and race, unknown no resubmit, desktop/mobile/focus, SO-01 regression. Physical device/screen reader coverage remains separate. Independent Security exact-source review then Manager acceptance.
