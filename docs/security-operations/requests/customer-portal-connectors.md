# Future customer portal — Security connector requirements (owner direction)
2026-11-25. Architecture request only; no SO-03, customer portal, real API, credential storage, grant activation or commissioning authorized. Security owns identity/authentication/authorization; Customer & Sales owns canonical business customer identity and relations; Manager owns sequencing and shared dependency register.

## Owner requirements
One future Hobby Corner portal should cover available X-Series customer portal functions and Hobby Corner-managed special orders, consignments, credit, rewards and other customer-related services. Verify actual X-Series API coverage and supported identity integration before promising parity. Physical-store customers need no email or online account; web orders collect email. Optional online account linking must preserve existing canonical customer IDs and historical relationships. Passwords securely hashed by HC Secure, optional email-code or authenticator MFA, verified recovery and enrollment; never copy vendor passwords or store credentials in business services. Employee routine access should support product View/Edit/Create, placeholder creation for special orders, customer information lookup; inventory adjustments restricted/flagged, exact policy TBD. Customer access own-record only.

## Security-owned connector requirements for future tool adoption
- Separate customer principal type and staff/owner authority; trusted session context with opaque principal and canonical customer binding, tenant/environment/audience, revision/expiry/revocation. No client-supplied ownership or cross-tenant/staff escalation. Verify current link on each protected request.
- Verified staff-assisted linking with short-lived single-use intent and code, verified email, independently authorized target record, conflict/duplicate handling, replay protection, auditing and readback. No automatic email/name/phone match or enumeration; recover/unlink/revoke safely; handle customer merges and changed contact details without silently transferring financial access.
- Domain APIs own customer records, credit, sales, special orders, consignment, rewards; Security owns only authentication, binding, capability/effect admission, session lifecycle, authorized projection and audit authority. No direct protected DB access or duplicate identity system. Canonical customer ownership verified in domain backend, no reliance on UI filtering, no broad customer search for customer principals.
- Reusable explicit read capabilities and authorized field projections, separate per-domain status/provenance/freshness, deny/unavailable without leaking unrelated records, paginated scoped reads, no raw vendor credentials or internal notes. Customer writes separately designed and gated; no financial mutation implied by read access.
- Security to propose exact versioned contract and fictional personas/negative fixtures: unlinked customer, linked customer A/B, stale/revoked link, duplicate identifiers, wrong tenant/audience, spoofed customer ID, cross-customer search, denied fields, unavailable backend and staff/customer session confusion. Account recovery and optional MFA must not weaken link ownership.
- Security Operations future connector consumer: authorized staff linking/status/recovery projections, never password setting or secret exposure; separate customer/staff surfaces, safe status, independently authorized readback. No executable client until exact Security-approved contract and Manager release.
- Coordinate existing F18 customer identity linkage, Customer & Sales, Core shared API and Manager. Future portal and integrations remain separately allocated; existing HC-ADMIN mock 0.2.0 and HC-AUTHZ/0.1.0 unchanged. No actual customer records in fixtures. Preserve existing HC Secure infrastructure and Owner/employee enrollments.
