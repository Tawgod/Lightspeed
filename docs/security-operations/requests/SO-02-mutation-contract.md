Please publish versioned exact schema and scripted examples (positive and negative), including compatibility and required dependency hashes. The following are semantic requirements/questions, not proposed field names or wire enums:
1. Role configuration and membership: supported changes and capability identifiers per read/edit/preview/confirm/status/readback; role revision and complete-vs-partial membership projection, safe add/remove vs replace, role creation/deletion if supported, impact on multiple employees; identity, tenant/environment, target and current policy/revision binding. Which role/assignment fields may be edited? What constitutes safe independent readback?
2. Direct grants/restrictions: distinct actions and stable assignment identities; canonical operation IDs and labels, tool/domain search, admissible operation status and unresolved aliases; backend-supplied typed location/resource/field options and dependencies, required/optional dimensions, explicit scope completeness, no implicit wildcard or cross-product. Scope-specific restriction precedence and conflict/prerequisite summaries must be backend supplied. Expiration/permanent eligibility, UTC precision/display timezone, historical/expired projection, allowed bounds, reason requirements and server clock basis.
3. Preview: exact immutable intent/target/scope/actor/session/tenant/environment/revisions/policy binding, unique request correlation, preview identity and expiry, safe gained/lost scope and affected employee projection, explicit confirm eligibility, conflict/prerequisite/approval/assurance outcomes; changing any intent invalidates preview. Need exact approved shape, completeness, expiry semantics, handling omitted/malformed/sanitized fields and denied preview. No UI permission computation.
4. Confirm: explicit single submission of approved preview, immutable identity and idempotency semantics, duplicate same vs conflicting intent, stale/revoked policy/target/session/preview, atomic synthetic commit and safe status reference; approval pending/step-up, independent authorization, no automatic continuation/retry. Define if and how fresh proof/approval leads to a new preview or explicit confirmation without credential collection. Define terminal versus uncertain transport failures and when a fresh explicit attempt is permitted.
5. Independent status and readback: authorized status reference projection, pending/committed/denied/unknown semantics, correlation with original immutable intent, safe status recovery when navigation/context lost or reference unavailable; no status disclosure to revoked actor, no cross-actor inspection assumed, no rollback/retry inferred from readback denial. Exact matching committed readback evidence and safe projection, stale result, independent capability and policy checks. Clarify what UI may retain in memory for status-only recovery, no persistent cache.
6. Envelope/fixture transport: versioning and compatibility with SO-01, exact adapter-origin metadata and unique invocation IDs, method/args/context generation/expected policy match, nonblank bootstrap policy, immutable complete args, current failure clearing and stale success/failure suppression. Mutation-specific handling if response suppressed after dispatch, never infer no effect. Explicit safe non-ok metadata whitelist; no raw payload or hidden record disclosure. Provide scripted examples for each supported action and failure, including missing capabilities, mismatch, expired preview, policy/revision conflict, duplicate confirm, pending approval/step-up, unknown outcome, delayed responses, denied/malformed readback. Confirm permissible separate fixture use without importing Security evaluator into UI runtime.
7. Exclusions: employee number remains separate authorized Timeclock/Security projection request; settings freshness remains separate design request; no real credentials/permissions/settings, SO-03 or HTTP integration. Confirm unresolved owner policy values and any unsupported actions remain disabled.
