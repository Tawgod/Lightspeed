# Core M7 — execution/access separation and remote mutation coordination
Status: proposed additive offline interface; requires Manager, Security S2.5F and Catalog review before executable changes. Exact V6 parent 0ffe5e3e152174462240021c59f64862af782b03. All M4/M5/M6 exports and persisted fingerprint semantics remain unchanged.

## Source review / local transaction
M6 fingerprints the entire frozen command including readEffects, reconcileEffects, approval and receiptFields. Changing an otherwise authorized disclosure field therefore conflicts with the same key. Approval is included in that fingerprint, making direct approval binding to the resulting digest circular if the approval itself contains that digest. M6 uses injected verifyLocked for effect/approval verification only on fresh execution; subsequent authorization callbacks must enforce current approval, including replay, precommit and disclosure. M6 authorizes independent read/reconcile effects, but domain projector remains trusted and receives a minimal receipt; no general field filter or durable Security proof. M6 command claims and audit do not prove real Security or revocation fencing.

Propose a new opt-in versioned execution identity, with immutable tenant/environment, actor/delegation identity, stable command namespace/key, exact execution effects/typed targets/revisions and normalized intent/payload. Separate stable execution digest from approval proof and independently requested access effects. Define approval binding to execution digest, actor, revision/effects and reviewer/expiry; retain immutable approval reference/evidence at original execution and independently validate current proof/policy at every required stage. Never refresh approval to authorize altered intent. Security decides whether replacement approval for identical committed execution may authorize disclosure; default deny until agreed. No session tokens or volatile policy epoch in identity. Distinct execution targets/effects/actor conflict; exact same execution with changed permitted access request can replay without new execution. Do not reinterpret existing M6 stored fingerprints or share unversioned command namespaces.

Proposed callbacks: verifyExecution/authorizeExecution at admission, post-claim, post-lock, precommit and current disclosure/reconciliation checks; verifyApproval with same digest and stage, current trusted clock/status; authorizeAccess with immutable execution plus independently normalized exact read/inspection tuple, purpose/audience and decision stage. Keep approval/execution decisions separate from access; no read-only grant can execute. Scope facts include exact tenant/env/location/resource/field, typed amount/quantity/currency/revision and relationship evidence when applicable, no arbitrary string encoding of monetary thresholds. Related targets outside execution set deny until trusted derivation agreed. No raw credentials, no browser effects, no implicit aliases, no union of unrelated grant dimensions. Security retains policy/decision ownership. S25D conservatively requires current execution grants and approval for disclosure; expired approval denies disclosure but never implies rollback. Independent historical receipt inspection by another actor remains a separate unresolved workflow, not a bypass. Reconciliation checks independent inspection grants before accessing committed state. Avoid leaking existence or receipts on denial; outcome classification is not authorization to view details.

Receipt schema is server-owned and versioned separately from requested output fields; bind immutable internal receipt shape to execution version, validate exact allowed keys and values, no sensitive payload. Fresh trusted projection after commit/replay, scoped read checks before/after output; do not allow caller to supply arbitrary projection. Consider projected field allowlist as defense in depth, not substitute for domain validation. Preserve unknown outcome and no blind reexecution. Core must not claim distributed revocation atomicity.

## Remote mutation seam — Catalog M9 coordination
Existing createAuditedLightspeedMutation authorizes one operation and scopes idempotency by tenant/environment/operation; payload digest alone does not enforce actor/effect identity. createLightspeedIdempotency returns verified stored result immediately on replay and only calls verifyReadback after fresh dispatch. Same key prevents repetition but different keys can claim the same business intent. Catalog M8 wraps synthetic checks and binds actor/approval into payload; no durable cross-key reservation or real causal vendor evidence.

Propose separate additive offline remote orchestrator contract, never wrap vendor dispatch in local database transaction. Reuse existing fingerprint/audit contracts where compatible. Atomic durable reservation of canonical domain intent identity (tenant/environment + domain-defined business uniqueness keys, e.g. normalized exact SKU/create target or revision-bound update intent), independent of transport request key and actor, plus execution digest binding. Distinguish same intent under another key (conflict or authorized replay, decision pending) from genuinely new revision/intent; different actor cannot retrieve prior result. Multiple uniqueness keys reserved atomically in deterministic order; no fuzzy identity, preserve leading zeros. No blanket content hash as sole duplicate key. Persist claim/dispatch state and lease before any synthetic external call, audit requested before dispatch, rederive exact effects and revision and reauthorize all execution/approval at dispatch boundary; pre-dispatch denial classified separately only if provably no dispatch, never release ambiguous reservation automatically. After dispatch verify causal correlated readback against intended target/revision/effects, not merely matching current values. Persist minimal verified receipt and append audit; after-commit/audit/projection failure does not permit repeating effect. Unknown pending/ack/readback/storage outcomes block same and alternate keys; separate current reconciliation authority and exact causal evidence, no automatic retry. Replay must recheck current execution/approval and independent read projection, not return stored vendor object. Actual external writes, production durable store, restart/network causal guarantees and release/retention policy remain gated.

Catalog: confirm domain uniqueness keys, normalized source/variant/supplier scope, create/update revision semantics, causal evidence/readback and same-intent alternate-key behavior; no new independent Core adapter. Security: confirm execution digest vs approval binding, decision stages and independent access scopes, historical inspection and safe outcome taxonomy. Manager: accept exact interface before implementation and coordinate dependency pins. Inventory/Purchasing/Customer: preserve M6 compatibility, review receipt and financial/physical distinctions, no migration until explicit coordination.
