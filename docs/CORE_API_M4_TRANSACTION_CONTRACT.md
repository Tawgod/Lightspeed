# M4 local transaction and cross-tool capability candidate

Approved V3 parent: 098c9e51ea4c3449605ad6951baa8284e126e8d4. Offline only.

## Proposed shared adapter contract (review before adoption)
createLocalTransactionCandidate({transaction, authorize, auditDenied}) accepts a trusted server-owned command with scope, key, operations, context, payload and apply. The candidate accepts test scopes only; no production route or writer. Operation names in fixtures are examples, not the Security registry. Required operations must be derived by trusted server code from the actual requested effects, never supplied by a client or inferred from tool identity. Security must approve actor/resource/field/environment binding and grant revocation semantics. Every required operation must receive literal true, before transaction and after claim/lock, including replay. A tool/workflow grant never substitutes for the underlying grant. No service-account bypass.

transaction(work) must use a single checked-out connection; begin, call work(tx), commit only on success, rollback on error. tx.claim atomically claims scope/key/fingerprint and locks competing command; returns claimed, replay with committed safe result, or conflict. tx.complete persists a safe JSON result; tx.appendAudit persists metadata, not payload. apply(tx,payload) re-reads and locks domain state, writes domain records and outbox in the same transaction, returns safe result. Never call a vendor, send a notification or run an external side effect inside this transaction. Outbox dispatch is a separate authorized, idempotent worker; delivery and remote uncertainty are not implemented. auditDenied records denial outside rolled-back transaction and must be durable; no sensitive payload. Adapter failures fail closed; commit-ack loss requires inspection/reconciliation rather than assuming rollback. Actor binding, transaction timeouts, safe replay projection, immutable audit storage and real outbox delivery remain review requirements. Existing remote mutation idempotency and audit adapters stay unchanged; do not conflate unknown vendor outcomes with local rollback.

## Inventory coordination
Inventory M6 may use the contract as a test-only injection seam, not a production persistence adapter. Count observation identity: session/scan; restock confirmation identity: task (version checked under lock); reason revision identity: code/revision. Use canonical tenant/environment/operation scope, stable key across tools, payload fingerprint, row locks and uniqueness constraints. Re-evaluate plans from trusted state inside transaction; persist confirmation, reviews, outbox and audit atomically. Never apply stock effects from restock evidence. Domain owners define records and validation. No schema migration proposed here; PostgreSQL fixture tables are disposable only.

## Operation map for Security review
Product Manager, Scanner, Special Orders, Purchasing, direct API, bulk import, automation: any actual product creation requires the same canonical product-create grant. Composed workflows require every actual effect grant; updates that modify wholesale cost also require the distinct cost-modification grant. Ordinary active employee product access includes wholesale cost viewing, no elevated cost-view permission. Anonymous/inactive actors denied. Map all remaining entrypoints (including Consignment, Preorders, RMS migration, invoice updates) before actual migration; representative synthetic tests are not a verified inventory of live endpoints. Read, create, update, approve, execute distinct. Queued work rechecks at execution, not just enqueue. Security owns all real roles, identity and decisions.

## Tests and limitations
Disposable PG tests cover concurrent claim/replay, fingerprint conflict, atomic domain/outbox/audit/claim rollback, denial after claim and denied replay. Synthetic capability tests cover representative tool/direct/import/automation denial, composed grants, missing/ambiguous/unavailable decisions, ordinary employee cost visibility, separate cost modification and production scope rejection. Test-only PG adapter is not durable production implementation. No dependency lockfile change: manager should coordinate pinned Node/npm, lock generation and npm ci. No POST-for-read activation.

Stop at manager/Inventory/Security interface review. No live routes, data, migrations, grants, merges or deployment.
