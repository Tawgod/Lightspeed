# Customer identity and consent evidence — M5 internal candidate

Baseline V2: 2365de8af4e8d69b162f6909d1f78be246e74fdf. Offline development only.

The customer identity evidence model is a business-data read model, not a login or authorization system. Use createCustomerIdentityRead with the existing customers reader plus trusted injected readLinks/readConsents functions. Provider adapters are not implemented or connected. Use the Core-owned createCoreReadExecutor with Security-owned exact grants, not an independent permission mechanism. The operation name customers.identity.read is a fixture proposal, not an approved grant.

Input link rows: exact customerId, provider (discord/rewards/customer-portal), exact externalId, status (verified/unverified/revoked), observedAt (UTC timestamp). Consent rows: exact customerId, channel (email/sms/discord/messenger/whatsapp/phone), status (opt-in/opt-out/unknown), evidenceId, observedAt. These are normalized source evidence, not assertions accepted from a browser. Each evidence list is bounded at 1000 rows. Source ownership, authoritative proof and timestamp freshness must be established by the provider adapter; this model does not establish either.

Output includes customerId, supplied-evidence-only coverage, status per provider/channel, conflict and review indicators, and canSend:false. External identifiers, contact addresses, notes, evidence IDs and raw records are not returned. Missing evidence is unknown. Multiple distinct accounts or contradictory link states require review. An opt-out dominates an opt-in even if the latter has a later timestamp; resolving legitimate re-consent requires separately agreed policy and evidence. No channel preference constitutes send authorization. No cross-customer global uniqueness, identity proof, current consent/freshness or complete provider coverage is asserted.

The existing shared customer reader retains get/search/searchFirstPage and supports optional correlationId on each; without it the existing call shapes remain unchanged. The Core read executor fixture demonstrates denial before I/O, sanitized failures and correlation propagation. Existing Special Orders route-source parity tests are retained and rerun, including the stricter malformed-envelope rejection; actual HTTP error compatibility remains for Core/feature owner review.

Do not link accounts, create customers, change consent, send notifications, mount routes, expose raw data or deploy. Next gates: manager review of operation/grant and projection policy, authoritative provider mapping, freshness and consent-purpose policy, Special Orders error mapping, and combined regression. No new CI workflow; run local node --test tests/customer-identity-m5.test.mjs tests/customer-sales-evidence.test.mjs and include both in next manager validation.
