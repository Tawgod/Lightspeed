# Owner setup — existing Timeclock account, no outside identity provider

**State (November 10, 2026):** Development-only proposal. No live account, production DB, operator activation, WebAuthn enrollment, or Railway service has been changed.

## Intended enrollment

1. The deployment administrator identifies the exact **already-existing, active Timeclock employee ID** through the canonical server-side Timeclock service. Do not use a name typed into a browser, the first user to open the UI, a Discord role, or a four-digit PIN to select the Owner. No identity document or external business identity verification service is needed for the product workflow.
2. During an approved, short setup window, a trusted operator provisions the target ID, a random **32-byte secret** generated by a cryptographically secure generator, and a **SHA-256 digest only** of that secret into the separately protected `hc_first_owner_activations` database table. The activation expires within 15 minutes. Store no plaintext activation secret in the DB, repository, logs, environment files, or ChatGPT.
3. The operator delivers the secret privately to the intended employee, not through a public link or chat transcript. The employee signs into the **existing Timeclock account** and uses the dedicated HTTPS Owner activation screen (not yet built) to register a WebAuthn passkey with local device user verification. The app confirms the signed Timeclock session, server-configured exact employee ID, an unconsumed matching digest, and zero existing Owners.
4. The registration must consume the challenge, verify true WebAuthn origin/RP ID and user verification, then commit the first passkey, Owner principal, activation consumption and append-only audit in **one PostgreSQL transaction**. On any failure the transaction rolls back and the challenge cannot replay.
5. After registration, disable the initial activation service and invalidate the secret. Log into the protected Owner Admin menu, verify passkey step-up, then enroll Google Authenticator on **the same Timeclock employee ID** using the existing factor service and verify the six-digit TOTP before activating it. Provide recovery codes only through protected UI. The original PIN remains unchanged.
6. Once primary Owner works, let a freshly strongly authenticated active Owner appoint another active Timeclock employee as Owner through the audited Admin permissions flow proposed in PR #52. Never allow any Owner role change via PIN-only or browser-side role claims. Retain a protected recovery process and prevent accidental removal of the final Owner.

## Implemented in draft PR #53

- `db/hc_first_owner_operator_activation.sql`: un-applied, strictly bounded one-time activation state, hash-only secret storage, audit event with immutability trigger.
- `services/security/operatorFirstOwnerPasskeyCandidate.js`: **test-mode-only, unmounted** backend composition with canonical active Timeclock identity verification, exact operator-selected employee ID, constant-time digest comparison and the already tested passkey transaction callback.
- `tests/operator-first-owner-postgres.test.mjs`: disposable PostgreSQL end-to-end database contract with mock WebAuthn verification, wrong token/employee, no-approval, audit-write failure rollback, challenge replay rejection and one-time success.

## Before a live setup

- Review database roles: only operator has INSERT on activation facts; runtime role gets SELECT and limited UPDATE of `consumed_at,credential_id`, with RLS or strict privilege separation. Do not use the same DB credential as the operator.
- Integrate actual TLS-only activation UI, restricted session proof, no-store/referrer protections, CSRF controls, per-IP + employee throttle, and never log/replay a secret. No API for issuing approvals to an unauthenticated visitor.
- Reconcile the single-Owner original index with PR #52's multi-Owner model **before any deployment**. Migrate first Owner once; subsequent Owners exclusively through strong-auth Admin.
- Verify actual account mapping via authorized server-side lookup, and accept WebAuthn with a real phone or security key, not mock fixtures; verify TOTP and recovery separately.
- Run full mandatory authentication/permissions/deployment checks and request owner approval for production migration, runtime route mount and actual first-Owner grant. Do not auto-deploy from this draft.
