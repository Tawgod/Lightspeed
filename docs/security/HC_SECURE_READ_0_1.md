# HC-SECURE-READ/0.1 candidate — server-only consumer interface
S2.5N independent candidate; requires Core/Catalog reciprocal review and Manager acceptance. HC-AUTHZ/0.1.0 #121 remains unchanged. No mutation/approval required for reads. No browser-facing generic authorization API.
 
## Context
Only Security's authenticated server adapter creates an opaque in-process context handle, never serialized to browser or accepted from request JSON. Server resolves principal realm employee, canonical employee ID, tenant, environment, audience, session binding, device binding, site binding (nullable offsite), assurance method, policy revision, evidence revision and earliest expiry. Handle is bound to one Security instance, not transferable across services; cross-service authentication transport separately approved. Re-read current identity/session/authority and evidence before protected disclosure; deny inactive, revoked, expired, unknown, mismatched audience or stale revisions. No authority from Scanner role or Timeclock permissions. Actual site/device and strong verification only through existing approved trusted adapters; no fallback to client claims.
 
## Read scope
Server-owned request exact {version:"HC-SECURE-READ/0.1",requestId,operation,tenant,environment,audience,location,resourceType,resourceId,variantId,sourceRevision,sourceRef,fields,purpose}. IDs opaque nonempty strings; variantId nullable; fields nonempty unique exact names, no wildcard. SourceRef and revision independently admitted by domain backend, complete source observation required. First Catalog slice one product, nullable verified variant, field name only, exact location, no listing/cost/vendor call. Each field requires both current read and projection authorization on exact complete tuple. No artificial command digest, execute effects or approval. Deny whole requested set if any field unauthorized; no partial leakage/counts. Domain owns source admission and projection construction. 
Return exact {version,requestId,status,data}; status ok/denied/unavailable/stale; data null except ok, when data contains only requested authorized fields (no identifiers/metadata unless requested and independently authorized). Generic safe denial; no resource existence oracle, raw errors or permission details. Protected result must not be cached, logged or reused after authority changes. Server transaction rechecks current authorization immediately before returning sanitized result; no claim that network delivery or separate DB source read is atomic with revocation. No arbitrary consumer callback holding a Security DB transaction; define reviewed bounded projection adapter at integration allocation. 
Independent receipt inspection remains distinct current operation, actor and immutable original command/approval/target/revision binding; no replay/release authority. Durable local consumption must share approved transaction/fence with all cooperative writers; cross-DB/remote dispatch needs durable intent and unknown hold, not a distributed atomic guarantee.
 
## Compatibility gates
Core and Catalog review exact blob and return explicit acceptance or corrections, minimal path manifest and source admission/projection strategy. No consumer implementation in S2.5N. Actual authenticated context issuer depends on approved selected Timeclock identity contract and existing factor verification. No production activation, registry grant or successor substitution.
